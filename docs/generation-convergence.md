# 生成草稿的自动收敛

分批生成全部文件后，整体设计检查失败会自动进入修复阶段。设计说明与源码不一致时，仅修复模块职责、接口等设计元数据；结构检查存在阻断错误时，每轮最多修复 3 个已规划文件，再重新检查整个工程。每次运行最多 3 轮，每次模型请求最多尝试 3 次，避免持续消耗积分。

草稿、修复轮次、最近诊断和待修复文件均保存在原生成任务的 checkpoint。网络中断、积分不足、服务重启或达到本次轮次上限时保留进度；前端显示已保存文件数和“继续修复”。继续操作复用已有文件，完成尚未完成的修复计划后再验证，不重新生成整个工程。每次实际模型调用沿用原计费回调。

旧版本整体检查失败后清空签名的草稿，也可在校验清单、路径及所有补丁原文前提后恢复；存在文件冲突时停止，保留原 checkpoint。普通签名不一致仍走原有重新生成规则。

修复不写入文件、不执行命令、不修改设计约束，不增加清单外路径。通过检查后仍需走正常任务审批、执行和工程验证。本阶段解决生成前的设计与结构问题，不保证所有运行时或业务缺陷均已消除。

结构检查识别 TypeScript 的 interface、type、enum 和类／接口方法限定名，避免将真实的数据类型与泛型方法误判为不存在。TypeScript 的 spec/test 文件与 JavaScript 测试一样默认排除在生产模块职责检查之外；配置源码仍需说明职责。设计字段错误会指出具体路径、符号和字段，供模型定向修正。JavaScript／TypeScript 仍使用有边界的词法证据，并非完整类型分析。

验证：`PYTHONPATH=tests:. python3 -m unittest test_generation_repair test_large_generation -v`；浏览器回归 `tests/frontend_large_generation.cjs`。
